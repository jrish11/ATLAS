# Native approval prototype — not enabled

This directory is development work in a separate checkout based on restricted preview commit `09583b5`. No production code imports it, no flag is changed, and the Windows preview still blocks both Claude and Codex task dispatch. It is **not a functioning AI boundary** and must not be merged into a release or exposed as safe based on these tests.

`NativeApprovalSession.cs` holds session state in memory: task, canonical project string, requested scope, random session ID, expiry, a one-use request nonce, SHA-256 of the full provider request, allowed method, and an active thread/turn pair. Task, project, scope and request mismatches, duplicate JSON properties, display-control characters, expiry, denial and revocation fail closed. `NativeApprovalDialog.cs` uses owner-bound native WinForms dialogs with full read-only scrollable text, default Deny and separate task/action confirmation. `PrivateApprovalHost.cs` sketches bidirectional inherited anonymous pipes to a Python child. It is expressly prohibited for production or provider grants: a worker-supplied request and known thread ID do not establish native provider correlation. No file or WebView message carries a grant. `approval_client.py` checks session, nonce, digest and expiry and defaults to cancel on malformed output, mismatch, timeout or disconnect. The existing fake Codex server exercises the client callback without an account or model.

The host's `BindTurn` must only be called after a **trusted native provider transport** has independently verified the actual Codex thread/turn, permissions, runtime workspace root, provider config, inherited integrations, tool inventory and Windows sandbox. A direct native JSONL provider transport is now sketched in `NativeCodexTurn.cs` and `CodexProcessChannel.cs`; it never asks the Python pipe client to identify or approve a provider turn. It checks a returned profile, workspace root, approval mode and model before binding, then validates each request against the native-held session. These checks have not been compiled or tested on Windows and do not establish real sandbox enforcement. `WindowsProjectGuard.cs` opens each directory ancestor without delete sharing and rejects reparse points; its behavior and race resistance require Windows testing and independent review. Never accept a worker-supplied turn binding as trusted. The same-user OS threat model and anonymous-handle isolation, inheritance into grandchildren, process-tree cancellation and races must be verified, not assumed. The current child-side `from_host` initial context check cannot itself establish the identity of the other endpoint. Native UI spoofing, accessibility, modal cancellation, oversized Unicode, owner lifetime and stale dialog behavior need independent review and interactive Windows tests.

The prototype handles only command/file approval requests. Other server-requested permissions and user-input requests must continue to be denied by the Codex adapter. The sandbox and network constraints are labels until verified by the provider and OS; user confirmation does not create a sandbox. `ApprovalClient` timeouts return cancel, but a pending read thread may remain blocked until the pipe closes; it disables that client after timeout. Denial must remain the default after disconnect, unexpected JSON, replay or cancellation. No silent retry may assume a failed turn left the workspace unchanged.

## Tests

On any host, from the repository root:

```
python -m unittest discover -s native-approval-dev/tests -p 'test_*.py' -v
```

These are mocked protocol/provider tests only: no real account, model, network, or computer action. On Windows with .NET 10 SDK and Python 3.11+ selected, compile and run the isolated native-session and inherited-pipe/fake-child tests:

```powershell
$python = (Get-Command python).Source
$worker = (Resolve-Path 'native-approval-dev/tests/fake_pipe_worker.py').Path
$provider = (Resolve-Path 'native-approval-dev/tests/fake_native_codex.py').Path
$env:ATLAS_NATIVE_TEST_ROOT = $env:RUNNER_TEMP
dotnet run --project native-approval-dev/tests/NativeApproval.Tests.csproj -- $python $worker $provider
```

This Windows command has not been run. It does not exercise the native dialogs, any real Codex provider, actual sandbox enforcement, project identity, cancellation of a real model turn, or clean-machine behavior. The current Mac environment has no .NET SDK and cannot compile these C# files. Independent code/security review and those native checks are prerequisites before any production wiring or gate change.

The direct-transport tests use a fake child only, with an explicitly created scratch project. They cover accepted request, unsafe configuration, stale turn and cancellation during a prompt. Native executable provenance, isolated handle inheritance, provider protocol version compatibility, sandbox effectiveness, filesystem reparse races and any native-dialog cancellation races remain release blockers. In particular, provider configuration echoes do not prove an operating-system sandbox. Provider writes use a bounded queue and a two-second deadline, with cancellation triggering process teardown outside the authority lock. The fake never-reading provider test exercises cancellation and revocation during pipe backpressure. This code and its cancellation behavior still require Windows execution and independent race review; an already-delivered approval cannot be recalled. No production caller, UI bridge, or real-account invocation is included.

Authority leases and request deadlines use an injected monotonic elapsed clock, defaulting on Windows to `GetTickCount64`, including sleep and hibernation. Unix expiry is a display/client hint only. Tests inject wall and elapsed clocks without changing the OS clock. Writer dispatch checks native authority again, and revocation tears down pending writes; fake delayed-reader tests queue a grant behind a blocked frame, revoke or expire it, and check that the child never receives an accept. A write already in flight when revocation or expiration occurs has an uncertain outcome and cannot be assumed undone. Windows execution and independent review remain necessary. Reference: https://learn.microsoft.com/en-us/windows/win32/sysinfo/interrupt-time

Native provider startup now creates an explicit minimal Windows environment instead of inheriting credentials, proxies or custom base URLs. The default user-profile path is retained only as the existing account-location reference; real account behavior remains untested. The Windows project guard resolves and compares final handle paths, rejects ambiguous spellings/reparse points, and reopens every ancestor to compare volume and file identity. Native scratch tests cover environment canaries, trailing-dot and available 8.3 aliases, protected paths and an attempted in-place junction conversion. An OS denial of that conversion does not prove all reparse mutations are impossible. These checks do not establish OS sandbox isolation or close all same-user races; keep the feature disabled pending Windows execution and independent review.

The native provider transport tracks the actual JSON-RPC request ID and full payload digest per turn. A duplicate ID, including one reused with a conflicting payload, revokes the session and fails the turn without a second prompt or response; a request arriving after completion is not handled. Fake fixtures cover duplicate, conflicting, late and cancellation cases. As with any grant already in flight, a previous response may already have reached the provider and cannot be assumed undone. These are uncompiled development changes until Windows CI runs.

Pending grant writes link the session revocation token directly into the write deadline and recheck it immediately before starting I/O. A deterministic fake-child fixture revokes after the initial authority check but before the write and verifies no accept frame is observed. A revocation concurrent with an already-started write still has an uncertain outcome. The native test source also fixes the variable-shadowing compilation error reported by Windows CI 41238439329; this later revision still needs its own Windows compile and run.

After Windows CI 41238602781 compiled successfully but failed while recursively deleting the scratch junction fixture, the fixture now removes its own mount-point reparse tag with `FSCTL_DELETE_REPARSE_POINT` before deleting scratch. It reads back the tag and target, checks both fixture paths are within scratch, preserves an earlier assertion if cleanup also fails, and reports unexpected Win32 mutation errors instead of treating them as a successful denial. Guard rejection may surface as either `InvalidOperationException` or `Win32Exception`. The exact cause of the previous cleanup failure is not proven; the revised fixture still requires a Windows run.

Development-only privileged `thread/start`, `turn/start` and approval frames recheck the held project identity as well as native authority immediately before a queued write. Windows fake-child tests hold each kind of frame behind a blocked write and attempt an in-place project reparse mutation; if the operating system refuses that mutation, the test invalidates the guard and reports that narrower case. This check reduces a race but is not descriptor-bound sandbox isolation, and in-flight writes remain uncertain. The native tests require Windows CI; the production gate remains off.

The project-dispatch fixture now synchronizes explicitly: the fake child acknowledges receipt of the filler, the writer announces it has reached the privileged frame, and a latch holds that writer until after the project mutation. The test then requires a second identity check and channel closure. Thus a filler-write timeout alone cannot satisfy the assertion. This revised synchronization awaits Windows CI.

## Development broker and MXC checks

`NativeOwnerBroker` is an unwired, native-UI broker path with an immutable false gate. It holds the project guard, requires the native task and action dialogs, selects the explicit `windows.sandbox="mxc"` profile, and uses the direct native app-server channel. The release does not compile or call this broker. The configuration response is a preflight check, not proof that MXC enforces the desired boundaries. MXC can be unavailable or blocked by managed policy; the code must fail rather than silently fall back. Official guidance: https://developers.openai.com/codex/windows/windows-sandbox and https://developers.openai.com/codex/app-server . The broker does not invoke setup or change execution policy, firewall, ACLs, or startup settings.

`PinnedCodexExecutable` recognizes only the x64 `codex-x86_64-pc-windows-msvc.exe` in the official OpenAI `rust-v0.166.0` release, SHA-256 `9d563ee4e0441ff9d59d612013e0460ddf8e5709735c2d9f6b98b7ef8ca4eb42`: https://github.com/openai/codex/releases/expanded_assets/rust-v0.166.0 . No executable is downloaded or shipped. The digest pin and held read handle do not establish trust in helper binaries, parent path aliases, executable launch identity, installed account, future updates, or sandbox behavior; they are not release clearance.

`ContainedProviderProcess` creates the provider suspended with an explicit three-handle inheritance list, assigns it to a kill-on-close Job Object, and resumes it only after assignment succeeds. Tests exercise Windows argument quoting, an unrelated inheritable canary event, a forced pre-resume failure and a fake sleeping descendant. This implementation and these tests have not yet run on Windows; independent review remains essential. Job assignment can fail under existing job policy and fails closed. A Job Object is process-lifetime containment, not the Codex filesystem/network sandbox.

`sandbox_probe.py <locally-supplied-pinned-exe>` is an opt-in, no-account scratch test for an isolated Windows CI VM. It performs no download, installation, login, API/model call, or global configuration change. It asks the explicitly selected MXC sandbox to write inside its scratch project and fail to write to a scratch sibling. It is not executed in the default suite. It tests neither network denial nor broader filesystem or process containment, and its 30-second `subprocess.run` timeout does not prove descendant cleanup; run it only in a disposable isolated job until process containment is verified. The official binary and its sidecar/helper requirements have not been exercised by this project.

`codex-windows-release-evidence.json` records the exact x64 CLI, app-server, command-runner, sandbox service/setup and package hashes displayed by OpenAI's official release page. The files were not downloaded or independently hashed. The complete helper load graph and runtime binary verification are unresolved; do not treat these metadata values as proof of an installed executable or of safe redistribution. The optional Python MXC probe still launches separately with `subprocess.run` and does not use the suspended launcher, so it must stay confined to a disposable isolated VM pending its own containment review.
