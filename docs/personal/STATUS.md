## Build and rollback

`./build-personal-dev.sh` produces `build/Atticus Dev.app`. It does not install, launch, create a login item, import a signing identity or grant permissions. It uses `com.atticus.personal.dev`, an isolated `~/.config/atticus-personal-dev` profile and an ad-hoc signature; permissions may be requested again on rebuild. Telemetry and the upstream updater are disabled by the development profile. The bundle and ZIP are development artifacts, not a release or verified installation. Removing the development bundle and its separate profile rolls back the local development copy; it does not change the regular installation. The Obsidian Atticus area is separate and can be removed independently after reviewing its contents.

Do not use upstream `build.sh` for this copy: it overwrites `~/Applications/Atticus.app`, imports a signing identity, changes login startup and restarts the app. The unmodified upstream Swift build failed against the installed SDK because it referenced a macOS 27 menu API unavailable there; the development copy omits that cosmetic line. The stock Python self-test also assumes TradingView is installed and failed on this machine.

## Codex safety

The adapter implements JSONL initialization, project configuration inspection, thread start/resume, turn start, streaming and interrupt. It requests a restricted named profile, `on-request` approvals and a user reviewer. It disables supported hook/plugin/app/search feature flags, refuses inherited MCP entries and hooks, and disables discovered skills by exact path before restarting and rechecking. Command and file boundary requests are correlated to explicit user decisions in fixtures; permission-expansion, user-input and unknown requests remain denied. A synthetic configuration showed that `-c 'mcp_servers={}'` does not remove inherited MCP servers. The installed CLI 0.155.1 experimental schema supports a named `permissions` profile and explicit `runtimeWorkspaceRoots`; they cannot be combined with legacy `sandbox`. A disposable no-login app-server fixture confirmed the selected profile and roots, denied sibling reads/writes, an escaping symlink read, configuration writes and loopback connections, allowed workspace reads/writes, hid a dummy environment token, and verified all six discovered system skills disabled after restart. A separate fresh `CODEX_HOME` with the real home environment exposed 14 enabled skills (eight user-scoped and six system-scoped); exact returned `SKILL.md` paths disabled all 14 in an ephemeral override. The live manager guard remains closed pending real-project scope checks, UI approval validation and an explicitly approved live smoke test. No model task or API spend was used.

With a fresh temporary `CODEX_HOME` and no account authentication, the installed app-server acknowledged `initialize` and `thread/start`. This is protocol evidence, not proof that a real task is safe or functional. Codex login and API-key billing have not been tested.

## Destination management and recovery

Settings includes a local searchable destination list with owner-confirmed edit and forget controls. Each requires a native confirmation. A per-record local recovery file is created before changing the existing destination registry; restore is offered again after restart only while the complete registry still matches the recorded post-change version. A concurrent change causes restore to stop instead of overwriting it. Backups use mode 0600 and retain the previous destination record, including its URL; they must be treated as private local data. Unknown destination fields cause edits and deletion to stop without changing that record. No vault notes or credentials are read by this feature. Tests use synthetic records only; the WebKit/native confirmation flow has not been tested end to end.

This is not a unified memory manager: profile and rule controls already existed, but their deletion does not yet use this recovery mechanism. Projects, task/session memory, workflows and corrections are not all searchable or editable through a single interface. Comprehensive category-selectable export, verified private-folder exclusion across all categories, profile/workflow migrations and conflict-safe recovery for those categories remain implementation work. The existing safe export still contains only redacted owner-supplied preferences, with the limitations stated above.

## Schema-based memory index

Settings now shows a searchable, category-filtered index from the existing profile, rules, confirmed destinations and projects, workflow stores, destination corrections, agent state and recent-session records. It shows source, scope, confirmation and confidence when available. Configured journal folder exclusions filter project and task paths; sessions have no dependable project scope and are hidden when any folder exclusion is configured. Profile, rule, destination and workflow records generally lack reliable folder attribution, so these folder exclusions cannot reliably classify their text. The index refuses symlinked store files and does not read vault files. The metadata-only local export accepts explicit categories and structurally permits only enumerated category/source/scope/status values and bounded confidence/confirmation, excluding names, free text, paths, URLs and IDs. It is not a content backup or a comprehensive export. Legacy profile shapes are indexed without modifying their source.

The shared index is currently read-only. Existing profile/rule and destination controls remain separate; task/session records remain auditable, and unified correction/forget/restore operations across profiles, rules, projects, workflows, tasks, sessions and corrections are **not implemented**. They have differing upstream persistence and locking behavior and require coordinated changes and tests before they can safely claim conflict-resistant recovery. The metadata export cannot restore memory contents. The real UI and save panel have not passed a host-permitted end-to-end test. Do not treat these features as completion of the requested unified memory manager.

Destination edits and deletions now include a hash of the exact displayed record. The manager checks that revision under the destination registry's cooperative lock before applying the change. A stale confirmation fails without altering the newer record. This protects against Atticus's cooperating destination writers; an unrelated process that ignores the lock can still race a file replacement. The UI does not yet provide this operation for the other indexed categories. In particular, current workflow and session writers do not all share a transaction lock, so revision-bound, conflict-safe mutations there require coordinated writer changes and cannot be inferred from the destination test.

## Revision-bound profile, rule and project controls

The Memory index now offers confirmed edit, forget and restore actions for supported profile facts, canonical rules and confirmed projects. The displayed revision is checked under the same cooperative lock as each existing store's writers. Before each mutation it keeps a mode-0600 local copy of the complete previous store; restore requires the complete current store to match the post-change bytes and refuses excluded project folders. Because recovery copies the complete project registry, it refuses to mutate that registry if any project is excluded or unscoped while exclusions are set. Backup files contain private profile data and paths and remain local. A later change to any record in that store disables restore. Symlinks, legacy or unknown profile schemas, unknown fields on the selected record, and noncanonical rules are rejected for these mutations. Profile reads no longer rewrite unknown fields and existing profile writers reject them. Projects use their saved names; rules now migrate to stable UUIDs on an explicit write, and ambiguous legacy duplicates are rejected.

The older separate profile and rules editors now route supported changes through the same confirmed transaction path; unsupported or sensitive profile records are read-only there. Source-wide profile forgetting is unavailable in Settings until it has a recoverable transaction. The index does not provide editing for workflows or archive/restore for tasks or sessions. The metadata export is still not a restore-capable backup. Native confirmation and UI behavior have not been exercised end to end through the host-guarded WebKit environment; synthetic handler and store tests do not establish that result. Locks protect cooperating Atticus writers, not unrelated processes that ignore them.


## Workflow writer coordination

The shortcut and procedure writers now use one cooperative `workflows.lock` for complete read–modify–write operations, including failure demotion, confirmation promotion, learning, removal, usage timestamps and explicit shortcut creation. Promotion rechecks the commands after confirmation while holding the lock, and usage updates do not resurrect or promote a changed shortcut. Unknown shortcut fields and unsupported workflow shapes cause writers to reject the mutation. Legacy entries still normalize in memory without requiring a read-time rewrite. These changes do not yet implement Memory-index workflow or correction edit, delete or recovery, or stable UUID identities for rules and corrections. External processes that ignore the lock can still race.


## Rule and correction identity

Legacy rule text and destination corrections remain unchanged when read. On an explicit rule write, canonical rule lines migrate to a versioned Markdown representation with UUIDs; rule text is still shown without the metadata in Atticus. Duplicate legacy text is rejected when the requested record is ambiguous. Rule IDs survive edits and undo. On an explicit correction edit or delete, legacy destination corrections receive UUIDs under the destination lock, and existing unknown correction and destination fields are retained. Both categories bind actions to the displayed revision, reject stale legacy references after migration, and keep private local recovery copies. A restore refuses to overwrite a registry or rule store changed after the operation. Recovery of a first migration restores the old content in the new UUID-bearing representation.

Rule metadata changes the on-disk Markdown representation; tools that read memory.md directly without understanding the version header will see the metadata comments. The confirmation dialogs and real Settings UI have not been exercised end to end. Workflows, task/session archive and full restore-capable export/import remain incomplete.


## Settings-only foreground OpenAI and workflow recovery

The isolated development binary supports `--settings-only`, an early mode that opens the existing Intelligence-style settings page without starting the supervisor, audio recovery, onboarding, hotkeys, provider checks, or API requests. Its nonpersistent WebKit view accepts only a user-entered foreground OpenAI key. “Save and use OpenAI” writes a separate `foreground-openai` Keychain item and selects the Pi/OpenAI foreground configuration; it does not read, transfer, or change the Codex account setting. Keep the normal development app closed while saving. A settings-write conflict after Keychain accepts the key can leave the Keychain changed; the UI reports this uncertainty. The owner has not entered a key through this build, and the window has not been tested end to end.

The foreground OpenAI route uses an isolated temporary Pi profile, explicit OpenAI provider and model, and disables tools, extensions, MCP, sessions and startup network activity. It is text-only; model-driven computer control is unavailable on this route. Pi was not found on the checked PATH or common locations. No Pi installation, model request, paid call, or real Keychain access was performed. The real Pi version, real provider behavior and end-to-end interaction remain unverified. The normal upstream Pi provider mode is unchanged.

The Memory index also supports confirmed, revision-bound edit, delete and conflict-safe restore of saved procedures and shortcut steps. Editing steps demotes their replay confirmation until the owner confirms again. Task/session archive and restore, and a selected-category restore-capable export/import, remain unimplemented.
